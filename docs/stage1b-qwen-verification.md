## 发现与修正

首轮轨迹中的决策摘要明确指出“当前证据为模拟数据，需通过真实查询确认”，但项目所有业务工具均为 Stub，没有可供模型另行查询的生产系统。模型因此持续调用同一查询，触发 Java 的无进展停止条件。

保留 v2，新增 Prompt v3，明确当前运行的是模拟业务验收：simulated=true 表示数据来源，不表示工具没有执行或本次观察无效；在模拟业务条件下按相同业务规则判断，结论必须限定在模拟环境。未删除 simulated 标记，未更改证据校验、工具白名单、评分规则或场景标准答案。

当前 v3 面向这个仅有模拟业务工具的版本。将来接入真实适配器时，应把运行环境纳入明确的上下文契约并使用对应 Prompt，不能将模拟环境声明直接用于生产。

## 通过的最小闭环

在 synced 复测中，真实 qwen-flash 执行了两次决策：

1. 输出 CALL_TOOL，选择 `pos.order.query`，查询 A001 / O100。
2. Java 网关返回完整 FOUND 证据；模型输出 FINISH / ALREADY_SYNCED，并引用该次 Evidence ID。报告通过服务端校验，任务进入 COMPLETED。

本次模型决策 2 次，业务工具调用 1 次，活动耗时 2672 ms。同期固定 Workflow 调用 3 个工具，结论也正确。只有一个开发场景，不足以比较总体准确率、速度或成本优势；本地 Workflow 和外部模型耗时也不能直接代表真实业务系统环境。

没有业务写操作，POS 数据仍来自 Stub，历史根因未确认。真实的是模型推理请求与决策返回，不是真实生产订单状态。
